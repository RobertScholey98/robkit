Each install has a `robkit` command for its apps and its upgrades. Run it with `pnpm robkit <command>` in the install's folder:

```sh
pnpm robkit add notes
```

Every command refuses a folder with no `robkit.json`, which init writes, and says to run it in an install's folder. A command given an option it doesn't take, or the wrong number of arguments, prints usage text and exits 1. `robkit upgrade` prints its own. So does `robkit add` given options and no name, and `robkit migrate` given the wrong number of arguments. Otherwise it prints the usage text of every command, as `pnpm robkit` does with a command it doesn't have.

## robkit add

Adds an app to `apps/<name>`, from a stack's template or your install's own. With no options it asks for each, and then prints the same command with options. With any option it asks nothing, and needs the name.

- `--stack <stack>`. The stack, one of `start`, `react-hono`, `express`, `next` or `go`. By default, `start`.
- `--access <rule>`. Who may open the app, `owner` for only you, `open` for anyone signed in or not, or `roles` for some guests. By default, `owner`.
- `--roles <role,...>`. The guest roles that may open it, with `--access roles` only.
- `--icon <emoji>`. The emoji the hub's launcher shows for it. By default, 📦.

In an install with its dependencies in, it runs `pnpm install` for the new app. With `pnpm dev` running, `pnpm dev` then starts the app at once, and after pnpm's own output it prints:

```text title="What it prints"
Added apps/notes. pnpm dev started notes at http://notes.robkit.localhost:3000.
```

It refuses:

- A name that isn't a slug, one of the platform apps `core`, `hub` and `admin`, or an app the install already has.
- A stack, an access rule or a role list it doesn't take. `--access roles` needs `--roles` with at least one role, and `--roles` goes only with `--access roles`.
- An `--icon` an app's `package.json` couldn't hold, by the same rule `pnpm dev` reads it with.
- A React + Go app on a machine with no Go, before it writes anything.

[pnpm dev and your apps](/docs/run-an-install/pnpm-dev-and-your-apps/#add-an-app) says what happens with and without `pnpm dev` running, and how to use a template of your own.

## robkit migrate

Asks the `pnpm dev` running in the install to run an app's migrate script, so a new migration applies with no restart. It takes the app's slug.

```text title="What it prints"
pnpm dev migrated notes.
```

With no `pnpm dev` running, it migrates nothing, says so, and exits 0. Start `pnpm dev`, which migrates every app as it starts.

It refuses:

- No slug, or a name that isn't one.
- An app `pnpm dev` isn't running, or one with no migrate script when `pnpm dev` started it.

## robkit upgrade

Moves the install to a newer robkit, the newest or the version you give. It moves robkit's packages in the catalog to the new version, and adds or raises each other catalog entry the new robkit needs. It raises `packageManager` when the new robkit pins a newer pnpm. It replaces robkit's lint policy, and its Go module in an install with a Go app. It never changes your apps.

It takes one version, such as `0.2.0`, or none for the newest. An install made from a clone links to robkit's packages there, so it has nothing to move:

```text title="What it prints"
This install links to a robkit checkout, so robkit upgrade has nothing to move. Pull the checkout to update it.
```

In an install that runs the tarballs `robkit vendor` packed, it moves to the registry's copy of the robkit running it, then removes the tarballs. `pnpm dlx --package create-robkit robkit upgrade` runs the newest robkit on the registry for that. When the registry doesn't have the robkit running, it changes nothing and says what to run. [Upgrading robkit](/docs/run-an-install/upgrading/#move-off-the-tarballs-in-vendorrobkit) has the details.

It refuses a change that isn't committed, a running `pnpm dev`, a link where it writes, and a version that isn't newer than the install's. [Upgrading robkit](/docs/run-an-install/upgrading/) has each refusal, what it changes and how to undo one.

## robkit check

Checks that every app and shared package in the install keeps to [the layer rule](/docs/build-an-app/the-layer-rule/). It takes no options. It prints nothing and exits 0 when every file keeps to it, and otherwise prints a line for each place one breaks it, and exits 1:

```text title="What it prints"
apps/example/src/core.ts:1:28  Layer rule: an app or shared package reaches core over HTTP only, never through @robkit/core.
```

`pnpm lint` runs it first, so a break stops the lint too.

## robkit vendor

In an install made with `--link`, packs the robkit packages it links to into `vendor/robkit`, and points the install at them, so it builds without the checkout. For an install with a React + Go app, it copies robkit's Go module there too.

```text title="What it prints"
Packed robkit's packages into vendor/robkit. Commit it with the install.
```

| Option | What it does |
| --- | --- |
| `--from <checkout>` | Packs from that robkit checkout's folder, and packs again what an earlier run packed. An install with no link left takes a newer robkit this way. |

A run removes each tarball in `vendor/robkit` that the install no longer uses.

It refuses an install that neither links to a robkit checkout nor runs its tarballs, one that runs them when `--from` is missing, a `--from` folder that isn't a robkit checkout, and a checkout that lacks a package or the Go module the install needs. [Upgrading robkit](/docs/run-an-install/upgrading/#update-a-vendored-install) has the steps.

## robkit database-urls

Prints the `DATABASE_URL` of each app with a migrate script, core included, as `KEY=value` lines to set once as shared variables on your host. It reads the host's Postgres admin URL from `ROBKIT_ADMIN_DATABASE_URL`, and the install's database secret from `ROBKIT_DB_SECRET`. It takes no options.

```text title="What it prints"
CORE_DATABASE_URL=postgres://core:<the password robkit derives>@db.example.com:5432/postgres
EXAMPLE_DATABASE_URL=postgres://example:<the password robkit derives>@db.example.com:5432/postgres
```

It refuses an admin URL that isn't a `postgres://` URL, and a secret that's missing or shorter than 32 characters.

## robkit deploy

Brings the install's applications on Coolify in line with the install, as `coolify.json` describes it, then deploys them, core first. It reads `COOLIFY_URL` and `COOLIFY_TOKEN`. By default it deploys each app that is new, changed since its last deploy, or getting new variables.

- `--all`. Deploy every app.
- `--apps <list>`. Deploy the apps named, by slug, with commas between them.
- `--dry-run`. Read Coolify and write nothing to it, and print what each app would do and why. With no `COOLIFY_URL`, print each app's variables instead.

With no `COOLIFY_URL` and no `--dry-run`, it deploys nothing, as in an install's CI before Coolify is set up:

```text title="What it prints"
COOLIFY_URL is not set, so nothing was deployed.
```

It refuses:

- An install with no `coolify.json`.
- A `COOLIFY_URL` that isn't a web address, or no `COOLIFY_TOKEN` with it.
- A commit that isn't pushed to the branch `coolify.json` names, since that is what Coolify builds.
- An `--apps` list with a name that isn't a slug.
