Your app has its own Postgres schema and its own role, and nothing else in the install can read them. `pnpm dev` makes both, and applies your app's migrations each time the app starts. Your app connects as its role with `DATABASE_URL`, which `pnpm dev` sets.

## What your app can reach

- Its own schema. The role has it first on its search path, so a table named without a schema lands there.
- Nothing else. The role can't reach core's schema or another app's.

An app gets a database when its `package.json` has a `migrate` script. Every app `robkit add` makes has one.

## Add a table

This adds a table of notes to an app named `notes`. Run `pnpm dev` in one terminal, and the rest in another.

<StackSwitch>
  <Fragment slot="start">
    Declare the table in `src/schema.ts`, beside the example's. Use `pgTable`, never `pgSchema`. The role can use only its own schema.

    ```ts title="apps/notes/src/schema.ts"
    import { pgTable, serial, text, timestamp } from "drizzle-orm/pg-core";

    export const note = pgTable("note", {
      id: serial().primaryKey(),
      author: text().notNull(),
      body: text().notNull(),
      at: timestamp({ withTimezone: true }).notNull().defaultNow(),
    });
    ```

    Then write the migration, in the app's folder:

    ```sh app
    pnpm db:generate
    ```

    It writes the next file in `drizzle/`. Commit it.

    Add the next migration to `migrations/`, named so it sorts after the last. They run in name order.

    ```sql title="apps/notes/migrations/0002_add_notes.sql"

      id serial primary key,
      author text not null,

      at timestamptz not null default now()
    );
    ```

    Commit it. The migrations are built into the server, so the binary needs no files beside it.

Then apply it, in the install's folder:

```sh
pnpm robkit migrate notes
```

This asks the running `pnpm dev` to run the app's `migrate` script with the app's own `DATABASE_URL`. The app keeps running, with its connection and its password. Without `pnpm dev` running, start it instead: it migrates every app as it starts.

## Migrations

- A migration that has run is never run again. Each app keeps a record of what ran, in its own schema, so a second run changes nothing.
- Never edit a migration that has run. Add another.
- In production, an app's container runs its migrations as it starts, before it serves. Two containers that start together apply each migration once.
