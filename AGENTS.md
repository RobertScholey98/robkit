# robkit

robkit is a self-hosting kit. `npm create robkit` scaffolds an install, and `robkit add` adds apps with auth, a database schema and a subdomain built in.

- Domain terms are in `GLOSSARY.md`. Use them in code, tests, tickets and commits.
- The plan is `.scratch/kit/map.md`. Build tickets are in `.scratch/v0.1-build/issues/`, numbered in build order.
- The spec is the Claude Doc "robkit v0.1 spec" (https://claude.ai/artifact/MrC9JDG3NK2tSw7h6x2VV5). Where a ticket and the spec disagree, the ticket is newer and wins.

## Commands

```sh
pnpm install                              # Node 24, pnpm 11
pnpm create-install                       # init's questions, then an install linked to this checkout; pnpm dev in it
pnpm turbo run lint typecheck test        # what CI runs; needs Docker
pnpm format                               # Prettier
pnpm --filter <package> test              # one package
pnpm --filter @internal/e2e test:production  # three installs in Docker over https, one on bun; CI doesn't run it yet
```

## Layout

- `packages/create-robkit` is `npm create robkit`. With no flags it asks init's questions and ends by printing the flags that make the same install. Each choice is described once, in the table in `src/choices.ts`: its flag, question, options and labels, which options are coming later, and the template layer each option adds. The flag parser, the usage text, the wizard and the generator all read it, so a new option is one table entry plus its folder under `templates/`. Its `templates/` holds an install in layers: `base` (core, Compose, turbo, `packages/core-client`, `packages/theme` and the install's root `AGENTS.md`), `package-managers/<name>` (the manager's settings file, Dockerfile and CI workflow), `ui-kits/none` (the hub and admin without a kit), `ui-kits/<kit>` (a UI kit, below), `tools/<name>`, and `stacks/<name>` for apps, each with its own `AGENTS.md`. An ORM lays `orms/<name>/app` over every app: its schema, migrations, `migrate` script and the example's queries in `src/visits.ts`. Its `orms/<name>/AGENTS.md` is the section every app's `AGENTS.md` ends with. An option that adds dependencies with install scripts names them as `builds`, and the generator writes them into the manager's settings: pnpm's `allowBuilds`, or bun's `trustedDependencies`. Everything else that differs per package manager is one entry in the table in `src/package-managers.ts`: where the settings live (the catalog, `builds` and `--link`'s overrides), the lockfile, the install and run commands, and how the templates' pnpm commands are spelled. The templates are written for pnpm, and the generator and `robkit add` spell them for the install's manager as they write them. The generator lays the chosen layers over each other in memory, merging manifests, mounts the first generator's stack at `apps/example`, writes the catalog from robkit's own, and records the choices in `robkit.json`. `init` in `src/init.ts` is the one operation from choices to a finished install: generate, write, then with `install` install dependencies and initialise git. The command line and the whole-stack test both call it. The package's second command, `robkit`, runs in an install, which takes create-robkit as a dev dependency. `robkit check` is the install's layer rule, and the install's `lint` script runs it. `pnpm robkit add` adds an app. `robkit vendor` packs the packages a linked install uses into its `vendor/robkit`, so it builds without the checkout until the packages are on npm. `robkit database-urls` prints each app's production `DATABASE_URL`, and `robkit deploy` deploys the install to Coolify (`src/coolify.ts`, with `deploymentOf` in `src/deployment.ts` working out each app's variables). `addApp` in `src/add.ts` writes `apps/<slug>` from one of the stacks `robkit.json` enables, through the same `appFiles` the generator mounts the example with, or from the install's own `robkit/templates/<stack>` folder, which replaces robkit's template whole. It writes files only. The generator catalogs every enabled stack's dependencies, so an added app needs no new versions. The templates are an install's own files: the install lints and tests them, so robkit's ESLint and TypeScript skip them.
- A UI kit is one row of the choice table and two folders. `packages/theme/theme.css` holds the install's tokens, shadcn's variables, and only it sets them; the hub and admin draw with Tailwind classes named after them. Their screens draw every control through their app's `ui.tsx`, the seam a kit replaces, and its `Root` wraps each page, for a kit that needs a provider. `ui-kits/<kit>/install` is laid over `ui-kits/none`: `packages/ui` and the hub's and admin's `ui.tsx`, stylesheet and manifest, and nothing else. The option's `optInLayer` holds one folder per stack, laid over an app that uses the kit: the example app always, and an app `robkit add` makes unless `--no-ui-kit`. The shadcn kits share `ui-kits/shadcn/app`, since an app draws only with components both have. For a shadcn kit, `packages/ui` is shadcn's own output, committed rather than run at init, so init needs no network and its output is stable. `pnpm --filter create-robkit shadcn-kit <base> <kit>` regenerates it with the cataloged shadcn CLI and checks the dependencies shadcn adds are cataloged. Chakra's `packages/ui` is written by hand: Chakra's components re-exported from `@internal/ui`, a `Provider`, which `Root` wraps each page in, and a theme in `src/system.ts` whose every colour, radius and font names a variable in `theme.css`. Its layers set TypeScript's `module` to `preserve`, because Chakra's declarations import their own files without extensions, which `nodenext` won't follow.
- In an install, each `apps/<slug>` gets the subdomain `<slug>.robkit.localhost`. A slug is lowercase letters and digits, starting with a letter (`slugProblem` in `@robkit/dev`), and an app with a `migrate` script gets its own schema and role from the provision step, `provisionApps` in `@robkit/dev`, which then runs that script. `pnpm dev` runs the step before it starts the apps. The runner and the step run each app's scripts with the manager the install's root `packageManager` names (`packageManagerOf`). The dev runner tells each app its slug as `ROBKIT_APP`, and hands core the owner's apps as `ROBKIT_APPS`, a JSON list of each app's slug and what its manifest declares: the `robkit` field of its `package.json`, with who may open it (roles by name) and an emoji for the launcher. Core adds a new app with the rule it declares, or owner-only, and creates any role it names that the owner lacks. After that admin sets who may open it, and core keeps the owner's rule. The hub and admin call core only through `callCore` from the install's `packages/core-client`, whose `fakeCore` their tests answer from.
- `packages/` holds the published `@robkit/*` packages. In this workspace their exports point at `src`. Each also builds to `dist` with `tsconfig.build.json`, and `publishConfig` points the packed package there, because Node won't strip types under `node_modules`. A repo check packs each one and fails on an export that isn't JS.
  - `@robkit/core`, the backend.
  - `@robkit/session`, the session token's claims and cookie, and `requestGuard`, which runs the guard on a web-standard `Request` for the server adapters. It fetches core's public key once, so apps verify tokens locally, and keeps an app's access rule from core for a minute. `@robkit/session/lapsed` is the guard's 401 for a call whose session has lapsed, which `sessionFetch` reads. It imports nothing, so the browser can load it. `@robkit/session/addresses` turns an install's domain into its addresses: each app on `<slug>.<domain>`, the platform apps' names, the default domain and dev port, and whether a URL is on the install. Core, the guard, the hub, admin, the dev runner, init and the whole-stack test all take their addresses from it. It imports nothing either.
  - `@robkit/guard`, the pure guard, and `conformance.json`, the cases the guard and every adapter pass.
  - `@robkit/hono`, the Hono adapter.
  - `@robkit/start`, the TanStack Start adapter. It wraps the app's server entry, so routes and server functions get the viewer as `context.viewer`.
  - `@robkit/react`, the client helper. Its `sessionFetch` sends the browser through core's `/refresh` when a call finds the session lapsed, and hands every other answer to the caller.
  - `@robkit/dev`, the `robkit-dev` runner and proxy behind an install's `pnpm dev`.
- `tooling/` holds private workspace packages: the shared tsconfig, the shared ESLint config, repo checks that run as tests, a per-suite test Postgres, `@internal/test-session`, which signs session tokens and runs a fake core for the guard's and adapters' tests, and the whole-stack test. It generates installs linked to this checkout, runs each one's own checks, and takes a browser through each stack's example app in Chromium, on Drizzle, and in two more installs on Prisma and Kysely. The React + Hono install has Chakra, and its added Start app uses the kit too. The Prisma install has shadcn on Radix and the Kysely install shadcn on Base UI, and their added apps opt out of their kit. The Prisma install runs on yarn and the Kysely install on bun: each manager installs its install, runs its dev stack and its own CI workflow, from the e2e package's cataloged `@yarnpkg/cli-dist` and `bun`. axe checks every install's hub, admin and apps, a theme journey changes the theme's variables on the hub and checks every install's controls follow them the same way, and `E2E_SCREENSHOTS=<folder>` saves each page it checks. Its `test:production` vendors an install, builds each app's image from the install's Dockerfile, and runs the journey over https behind Caddy on `robkit.test`, once for each ORM, with Chakra on the Prisma install and shadcn on Base UI on the Kysely one, which bun installs and builds from bun's Dockerfile. A yarn install can't deploy from vendored packages, since turbo can't prune the lockfile they make, so `yarn-prune.test.ts` serves the packed packages from a local registry and checks that turbo prunes each app of a yarn install and the pruned install passes frozen. It takes about nine minutes and runs on its own. In WSL, if Docker can't pull images because of Docker Desktop's credential helper, point `DOCKER_CONFIG` at a folder with an empty `config.json`.

## The layer rule

`tooling/eslint` enforces each rule here, and its error names the rule. A new rule goes in with its lint rule, in the same commit.

- `@robkit/session` and `@robkit/guard` import no framework, and the guard does no I/O.
- Adapters (`@robkit/hono`, `@robkit/start`, `@robkit/react`) import session and guard, never core. Code reaches core over HTTP only.
- Core's tables live in the `core` schema, declared with `core.table()` in `packages/core/src/schema.ts`.
- An install has its own layer rule, for its apps. `robkit check` (`src/check.ts` in create-robkit, one row per rule) is its only implementation, so it holds whichever linter the install chose. The install's `lint` script runs it.
- Only the proxy may reach core, because core trusts `X-Forwarded-For` for its sign-in limit. Core listens on 127.0.0.1 unless `HOST` is set.

## Conventions

- Every external version lives in the catalog in `pnpm-workspace.yaml`, and manifests say `catalog:`. A test in `tooling/repo-checks` fails on any version pinned elsewhere. Peer dependencies are exempt.
- TypeScript stays on 6.0 until typescript-eslint supports 7.
- pnpm 11 refuses packages published in the last day. Pin an older version rather than adding an exemption.
- Relative imports use the `.ts` extension, so Node can run source files directly. ESLint enforces it.
