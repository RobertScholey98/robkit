# robkit

robkit is a self-hosting kit. `npm create robkit` scaffolds an install, and `robkit add` adds apps with auth, a database schema and a subdomain built in.

- Domain terms are in `GLOSSARY.md`. Use them in code, tests, tickets and commits.
- The plan is `.scratch/kit/map.md`. Build tickets are in `.scratch/v0.1-build/issues/`, numbered in build order.
- The spec is the Claude Doc "robkit v0.1 spec" (https://claude.ai/artifact/MrC9JDG3NK2tSw7h6x2VV5). Where a ticket and the spec disagree, the ticket is newer and wins.

## Commands

```sh
pnpm install                              # Node 24, pnpm 11
pnpm create-install                       # asks for a folder and the example's stack, then makes and installs an install linked to this checkout; pnpm dev in it
pnpm turbo run lint typecheck test        # what CI runs; needs Docker
pnpm format                               # Prettier
pnpm --filter <package> test              # one package
pnpm --filter @internal/e2e test:production  # the default install in Docker over https; CI runs it on main, nightly and PRs labelled production
```

## Layout

- `packages/create-robkit` is `npm create robkit`. Every install gets one stack: pnpm, Drizzle, shadcn on Base UI, ESLint with Prettier, Husky with lint-staged, and Vitest. Init asks only for the folder and the example app's stack, and ends by printing the flags that make the same install: `--stack`, and `--install` and `--link` when it was given them. `src/choices.ts` lists the stacks: the ready ones, then the ones coming later, which the wizard shows but can't pick. A new stack is one entry there plus its folder, `templates/stacks/<name>`. Every install offers every ready stack. `templates/base` is the install itself: core, Compose, turbo, the hub and admin, `packages/core-client`, `packages/theme`, `packages/ui`, the ESLint, Prettier, lint-staged and Husky config, the Dockerfile, the CI workflow and the install's root `AGENTS.md`. `templates/stacks/<name>` is one app, with its Drizzle schema, migrations and `migrate` script, and its own `AGENTS.md`. The Dockerfile builds an app in a turbo-pruned workspace, then deletes every `node_modules` and installs only that app's production dependencies, and runs it on the Node image without npm, Yarn or Corepack. So an app's `dependencies` are what its server imports, and what Vite bundles is a dev dependency: the hub's and admin's React, theme and UI kit. The generator reads `base` in memory, mounts the example's stack at `apps/example`, writes the catalog from robkit's own, covering every stack, and records the example's stack in `robkit.json`. Every install of one robkit version has the same `packages/ui`, `packages/theme`, `packages/core-client` and catalog. `init` in `src/init.ts` is the one operation from choices to a finished install: generate, write, then with `install` initialise git and install dependencies, in that order, so Husky's postinstall finds the repository. The command line and the whole-stack test both call it. The package's second command, `robkit`, runs in an install, which takes create-robkit as a dev dependency. `robkit check` is the install's layer rule, and the install's `lint` script runs it. `pnpm robkit add` adds an app. `robkit vendor` packs the packages a linked install uses into its `vendor/robkit`, so it builds without the checkout until the packages are on npm. `robkit database-urls` prints each app's production `DATABASE_URL`, and `robkit deploy` deploys the install to Coolify (`src/coolify.ts`, with `deploymentOf` in `src/deployment.ts` working out each app's variables). `addApp` in `src/add.ts` writes `apps/<slug>` on any ready stack, through the same `appFiles` the generator mounts the example with, or from the install's own `robkit/templates/<stack>` folder, which replaces robkit's template whole. It writes files only. The generator catalogs every stack's dependencies, so an added app needs no new versions. The templates are an install's own files: the install lints and tests them, so robkit's ESLint and TypeScript skip them.
- The UI kit is shadcn on Base UI, in the install's `packages/ui`. `packages/theme/theme.css` holds the install's tokens, shadcn's variables, and only it sets them; the hub and admin draw with Tailwind classes named after them. Their screens draw every control through their app's `ui.tsx`, which draws with `packages/ui`. Every app draws with the kit too, the example and each one `robkit add` makes. `packages/ui` is shadcn's own output, committed rather than run at init, so init needs no network and its output is stable. `pnpm --filter create-robkit shadcn-kit` regenerates it with the cataloged shadcn CLI and checks the dependencies shadcn adds are cataloged.
- In an install, each `apps/<slug>` gets the subdomain `<slug>.robkit.localhost`. A slug is lowercase letters and digits, starting with a letter (`slugProblem` in `@robkit/dev`), and an app with a `migrate` script gets its own schema and role from the provision step, `provisionApps` in `@robkit/dev`, which then runs that script. `pnpm dev` runs the step before it starts the apps. The runner and the step run each app's scripts with pnpm. The dev runner tells each app its slug as `ROBKIT_APP`, and hands core the owner's apps as `ROBKIT_APPS`, a JSON list of each app's slug and what its manifest declares: the `robkit` field of its `package.json`, with who may open it (roles by name) and an emoji for the launcher. Core adds a new app with the rule it declares, or owner-only, and creates any role it names that the owner lacks. After that admin sets who may open it, and core keeps the owner's rule. The hub and admin call core only through `callCore` from the install's `packages/core-client`, whose `fakeCore` their tests answer from.
- `packages/` holds the published `@robkit/*` packages. In this workspace their exports point at `src`. Each also builds to `dist` with `tsconfig.build.json`, and `publishConfig` points the packed package there, because Node won't strip types under `node_modules`. A repo check packs each one and fails on an export that isn't JS.
  - `@robkit/core`, the backend.
  - `@robkit/session`, the session token's claims and cookie, and `requestGuard`, which runs the guard on a web-standard `Request` for the server adapters. It fetches core's public key once, so apps verify tokens locally, and keeps an app's access rule from core for a minute. `@robkit/session/lapsed` is the guard's 401 for a call whose session has lapsed, which `sessionFetch` reads. It imports nothing, so the browser can load it. `@robkit/session/addresses` turns an install's domain into its addresses: each app on `<slug>.<domain>`, the platform apps' names, the default domain and dev port, and whether a URL is on the install. Core, the guard, the hub, admin, the dev runner, init and the whole-stack test all take their addresses from it. It imports nothing either.
  - `@robkit/guard`, the pure guard, and `conformance.json`, the cases the guard and every adapter pass.
  - `@robkit/hono`, the Hono adapter.
  - `@robkit/start`, the TanStack Start adapter. It wraps the app's server entry, so routes and server functions get the viewer as `context.viewer`.
  - `@robkit/react`, the client helper. Its `sessionFetch` sends the browser through core's `/refresh` when a call finds the session lapsed, and hands every other answer to the caller.
  - `@robkit/dev`, the `robkit-dev` runner and proxy behind an install's `pnpm dev`.
- `tooling/` holds private workspace packages: the shared tsconfig, the shared ESLint config, repo checks that run as tests, a per-suite test Postgres whose data stays in memory (`in-memory.yaml`, added to `COMPOSE_FILE` by `testComposeFiles()`), `@internal/test-session`, which signs session tokens and runs a fake core for the guard's and adapters' tests, and the whole-stack test. It generates two installs linked to this checkout, one with its example app on each stack, and in each adds an app on the other stack with `robkit add`. It takes a browser through each install's example and added app in Chromium. On the Start install it also runs the install's own CI workflow on a `PATH` that can't see any `node_modules/.bin`, checks that `pnpm lint` catches a cross-app import, and checks that the pre-commit hook refuses a commit that breaks the layer rule. axe checks every install's hub, admin and apps, a theme journey changes the theme's variables on the hub and checks its controls follow them, and `E2E_SCREENSHOTS=<folder>` saves each page it checks. Its `test:production` vendors the default install, builds each app's image from the install's Dockerfile, and runs the journey over https behind Caddy on `robkit.test`, which stands in for a Cloudflare tunnel into Traefik: it names each visitor in `CF-Connecting-IP` and hands every request through one hop, and two visitor containers check that core's sign-in limit counts them apart. It runs `src/extraneous-packages.js` in every image it builds, and fails on any installed package the app doesn't reach through its production dependencies. The images build with Husky's postinstall and no git. It takes about nine minutes and runs on its own. `production.yml` runs it in CI on every push to `main`, from `nightly.yml`, and on a pull request labelled `production`. With `ROBKIT_BUILD_CACHE` set to a BuildKit cache backend (`type=gha` in CI), each image builds with buildx and keeps its layers there, one scope per app, and every build prints how many of its steps were cached. No container starts or stops while a journey's browser is open, and each launch first waits until the host's interfaces have stayed the same for 3 seconds, since a container that just started keeps changing them for a moment. A failed production journey prints what the browser saw and each container's state and last logs, and the stack hands its prefix to `removeWhenGone`, which also removes the images it built. In WSL, if Docker can't pull images because of Docker Desktop's credential helper, point `DOCKER_CONFIG` at a folder with an empty `config.json`. A journey that fails prints what its browser saw (console errors, failed requests, 4xx and 5xx answers, and each open page's text) and what the dev runner said meanwhile. Where Docker runs natively on Linux, as on CI, set `COMPOSE_FILE` as `ci.yml` does, so every test Postgres runs on the host's network: each new compose network otherwise adds host interfaces, and Chromium fails its in-flight requests with `ERR_NETWORK_CHANGED`. Docker Desktop keeps its networks in its own VM, so the suite in WSL with Docker Desktop doesn't need it. A test registers what it starts with `removeWhenGone`: a detached watcher removes its Compose project and stops every process carrying its `ROBKIT_TEST_TAG` once the test process exits, however it ends, so a failed or interrupted gate leaves nothing running. A Postgres port comes from `freePostgresPort()`, which also skips the ports Docker already publishes, because Docker Desktop publishes them from its own VM where `freePort()` can't see them.

## The layer rule

`tooling/eslint` enforces each rule here, and its error names the rule. A new rule goes in with its lint rule, in the same commit.

- `@robkit/session` and `@robkit/guard` import no framework, and the guard does no I/O.
- Adapters (`@robkit/hono`, `@robkit/start`, `@robkit/react`) import session and guard, never core. Code reaches core over HTTP only.
- Core's tables live in the `core` schema, declared with `core.table()` in `packages/core/src/schema.ts`.
- An install has its own layer rule, for its apps. `robkit check` (`src/check.ts` in create-robkit, one row per rule) is its only implementation. The install's `lint` script runs it, then ESLint.
- Only the proxy may reach core, because core trusts `X-Forwarded-For` for its sign-in limit, or `CF-Connecting-IP` when `ROBKIT_TRUSTED_PROXY=cloudflare` says only a Cloudflare tunnel reaches the host. Core listens on 127.0.0.1 unless `HOST` is set.

## Conventions

- Every external version lives in the catalog in `pnpm-workspace.yaml`, and manifests say `catalog:`. A test in `tooling/repo-checks` fails on any version pinned elsewhere. Peer dependencies are exempt.
- TypeScript stays on 6.0 until typescript-eslint supports 7.
- pnpm 11 refuses packages published in the last day. Pin an older version rather than adding an exemption.
- Relative imports use the `.ts` extension, so Node can run source files directly. ESLint enforces it.
