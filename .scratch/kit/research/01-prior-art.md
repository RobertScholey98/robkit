# Prior art: Better-T-Stack, create-t3-app, shadcn CLI

Researched 2026-10-28 against the default branches of the three repos: Better-T-Stack at `a9bd456` (release 3.49.0, 2026-10-24), create-t3-app at `4709861` (2025-12-13), shadcn/ui at `96da9cc` (shadcn CLI 4.23.0, 2026-10-27). File links point at those commits. Star counts and issue counts are not given because the GitHub API was not reachable from this session.

## Answer

- **Better-T-Stack (BTS)** is the closest match to robkit. It layers template folders, one per option dimension, into an in-memory file system. Handlebars fills the templates, then ts-morph and JSON processors patch the result. It saves the choices to `bts.jsonc` so that a later `add` can read them. CI typechecks and builds a sharded, curated set of real combinations every day. `add` only adds addons and empty workspace packages. It can't add a new app, and it has no update path. MIT, very active.
- **create-t3-app** copies a separate file for each combination ("with-auth-db.ts") and tests the full valid matrix in CI. It supports only Next.js, has no `add` and no updates, and has been quiet since December 2025. MIT. Its source is a lesson in what not to copy.
- **shadcn CLI** is a file registry, not a matrix generator. Items are JSON lists of files, dependencies, env vars and CSS. AST transformers rewrite imports to fit the user's `components.json`. The only update path is `add <item> --diff` for one item at a time. It now scaffolds Turborepo monorepos, including a TanStack Start one. MIT, very active.
- **Recommendation:** write robkit's own small generator and don't fork either CLI. Copy BTS's shape: dimension-layered templates, a virtual FS, AST post-processors, a saved config that drives `add`, and tiered matrix CI. Put the platform code in versioned `@robkit/*` packages, so that updates arrive as dependency bumps rather than re-scaffolds. Use shadcn only where it is strong: let init install the chosen UI kit through the shadcn CLI, and optionally publish a robkit shadcn registry for UI blocks.

## 1. How each composes templates

**Better-T-Stack.** The engine lives in `packages/template-generator` and is published separately as `@better-t-stack/template-generator`, a "virtual file system generator… works in browsers and Node.js" ([package.json](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/packages/template-generator/package.json)).
- Templates are 532 files in folders named after option dimensions: `templates/{base,frontend,backend,db,api,auth,addons,examples,deploy,packages,…}`. Variants are subfolders, for example `frontend/react/web-base`, then `frontend/react/tanstack-start`, and `backend/server/base`, then `backend/server/hono` ([templates/](https://github.com/AmanVarshney01/create-better-t-stack/tree/a9bd456/packages/template-generator/templates)).
- `generate()` runs one handler per dimension in a fixed order into a `VirtualFileSystem`. Each later layer overwrites or adds files. Processors then edit dependencies, env vars, catalogs, auth plugins and the README, and the generator writes `bts.jsonc` last ([generator.ts](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/packages/template-generator/src/generator.ts), [frontend.ts](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/packages/template-generator/src/template-handlers/frontend.ts)).
- Files ending in `.hbs` go through Handlebars with `eq`/`includes` helpers ([template-processor.ts](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/packages/template-generator/src/core/template-processor.ts)). Edits that cross options are made in the code itself with ts-morph. For example, `processAuthPlugins` adds `tanstackStartCookies()` to `packages/auth/src/index.ts` when TanStack Start and Better Auth are both chosen ([auth-plugins.ts](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/packages/template-generator/src/processors/auth-plugins.ts)).
- A build script embeds the templates into `templates.generated.ts`, so the same engine also drives the web Stack Builder ([generate-templates.ts](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/packages/template-generator/scripts/generate-templates.ts)).

**create-t3-app.** It copies `template/base`, then runs one "installer" per package ([installers/](https://github.com/t3-oss/create-t3-app/tree/4709861/cli/src/installers)). An installer adds dependencies and copies whole files that were written ahead of time for each combination. `trpc.ts` picks between `with-better-auth-db.ts`, `with-auth-db.ts`, `with-db.ts`, `base.ts` and others ([trpc.ts](https://github.com/t3-oss/create-t3-app/blob/4709861/cli/src/installers/trpc.ts)). `template/extras/src/env/` holds eight env files, one for each auth × db × PlanetScale combination ([extras/src/env](https://github.com/t3-oss/create-t3-app/tree/4709861/cli/template/extras/src/env)). Templates have no templating language and the CLI has no AST edits. The number of files grows with the product of the options.

**shadcn.** Each item in the registry is a JSON object listing `files` (each with a `type` and an optional `target`), `dependencies`, `registryDependencies`, `cssVars`, `css`, `envVars` and `font`. Types include `registry:file`/`registry:page`, whose `~/`-rooted targets can place any file, and `registry:base`, which is a whole design system ([registry-item-json docs](https://ui.shadcn.com/docs/registry/registry-item-json), [source](https://github.com/shadcn-ui/ui/blob/96da9cc/apps/v4/content/docs/registry/registry-item-json.mdx)). Before writing a file, the CLI rewrites it with AST transformers for imports, RSC, icons, Tailwind prefix, RTL, fonts and CSS vars ([diff.ts imports](https://github.com/shadcn-ui/ui/blob/96da9cc/packages/shadcn/src/commands/diff.ts), [transformers/](https://github.com/shadcn-ui/ui/tree/96da9cc/packages/registry/src/transformers)). It also has updaters for CSS, dependencies, env and fonts ([updaters/](https://github.com/shadcn-ui/ui/tree/96da9cc/packages/registry/src/updaters)).

Project scaffolding is a different mechanism. `init --template <next|vite|start|react-router|astro> [--monorepo]` clones a starter folder such as `templates/start-monorepo` from the shadcn GitHub repo, then adds registry `files` on top ([start.ts](https://github.com/shadcn-ui/ui/blob/96da9cc/packages/shadcn/src/templates/start.ts), [create-template.ts](https://github.com/shadcn-ui/ui/blob/96da9cc/packages/shadcn/src/templates/create-template.ts), [templates/](https://github.com/shadcn-ui/ui/tree/96da9cc/templates)). `--base` picks the component library: `radix`, `base` or `aria` ([preset.ts](https://github.com/shadcn-ui/ui/blob/96da9cc/packages/registry/src/preset/preset.ts)).

## 2. How each tests combinations in CI

**Better-T-Stack.** It uses three tiers, named in its glossary: a fast default suite, a "matrix smoke" and a sharded "full matrix job". It deliberately doesn't cross every subset of addons ([CONTEXT.md](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/CONTEXT.md)). This is what the workflow runs:
- Format, lint and typecheck of the source.
- `test:ci`, which covers compatibility rules, adding to a project, MCP and the programmatic API.
- An 8-shard `generated-builds` job. It scaffolds about 60 curated samples, installs real dependencies, typechecks and builds them, and boots some of them as runtime probes, for example `bootAndValidateStartAuthRuntime`.

It runs on every PR and also daily by cron, "because an upstream release can break them with no change here" ([test.yaml](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/.github/workflows/test.yaml), [generated-builds.test.ts](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/apps/cli/test/generated-builds.test.ts), [samples.ts](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/apps/cli/test/generated-builds/samples.ts)). Invalid stacks are checked against expected errors ([compatibility.test.ts](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/apps/cli/test/compatibility.test.ts)). The glossary describes a full exhaustive matrix job, but I found no workflow at this commit that runs one.

**create-t3-app.** A script builds the cartesian product of 7 booleans and 4 database types, then drops invalid ones, such as both auth libraries at once or a database provider without an ORM. That leaves 216 combinations. Each one becomes a GitHub Actions matrix job that scaffolds the app and runs `pnpm build`. A separate 2×2 job covers ESLint and Biome. It runs only when a PR touches `cli/**` ([generate-matrix.js](https://github.com/t3-oss/create-t3-app/blob/4709861/.github/scripts/generate-matrix.js), [e2e.yml](https://github.com/t3-oss/create-t3-app/blob/4709861/.github/workflows/e2e.yml)).

**shadcn.** The `Templates` workflow covers 5 templates × npm/pnpm 10/pnpm 11/bun/yarn × app and monorepo mode. Each run scaffolds with the built CLI against a local registry and checks `packageManager`, `workspaces` and that no `workspace:` protocol leaks into non-pnpm projects. It then runs `typecheck` and `build` ([templates.yml](https://github.com/shadcn-ui/ui/blob/96da9cc/.github/workflows/templates.yml)). Other workflows validate and monitor third-party registries ([workflows/](https://github.com/shadcn-ui/ui/tree/96da9cc/.github/workflows)).

## 3. How users get updates after scaffolding

- **Better-T-Stack:** no upgrade command. The FAQ says "the CLI is for new projects", and `bts.jsonc` exists so that `add` can detect the stack ([faq.mdx](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/apps/web/content/docs/faq.mdx), [bts.jsonc docs](https://better-t-stack.dev/docs/bts-config)). The config stores a `reproducibleCommand` and the CLI `version` ([bts-config.mdx](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/apps/web/content/docs/bts-config.mdx)).
- **create-t3-app:** none. Its CLI flags cover creation only ([cli/index.ts](https://github.com/t3-oss/create-t3-app/blob/4709861/cli/src/cli/index.ts)).
- **shadcn:** updates are pulled one item at a time. `add <item> --diff` shows how the registry version differs from the local file. The old `diff` command is deprecated in its favour ([diff.ts](https://github.com/shadcn-ui/ui/blob/96da9cc/packages/shadcn/src/commands/diff.ts), [CLI docs](https://ui.shadcn.com/docs/cli)). The CLI v4 notes suggest asking an agent to "check for updates from @shadcn and merge with my local changes" ([2026-03-cli-v4.mdx](https://github.com/shadcn-ui/ui/blob/96da9cc/apps/v4/content/docs/changelog/2026-03-cli-v4.mdx)). `apply <preset>` re-themes an existing project, and `migrate` runs scripted codemods (`radix`, `rtl`, `icons`, …) ([cli.mdx](https://github.com/shadcn-ui/ui/blob/96da9cc/apps/v4/content/docs/(root)/cli.mdx)). The CLI doesn't merge three ways: `--overwrite` replaces the local file.

## 4. `add` command and option coverage

| | Better-T-Stack | create-t3-app | shadcn |
|---|---|---|---|
| Add to existing repo | `add --addons …` and `add --package <name>` (an empty `packages/<name>`), plus deploy targets. **It can't add a new app or frontend** ([AddInputSchema](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/packages/types/src/schemas.ts), [CLI docs](https://better-t-stack.dev/docs/cli)) | None | `add` installs items into any `components.json` project. In a monorepo you run it inside `apps/web` and it routes primitives to `packages/ui` ([monorepo docs](https://ui.shadcn.com/docs/monorepo)) |
| Package managers | npm, pnpm, bun (**no yarn**) | npm, pnpm, yarn, bun, read from the user agent ([getUserPkgManager.ts](https://github.com/t3-oss/create-t3-app/blob/4709861/cli/src/utils/getUserPkgManager.ts)) | npm, pnpm, bun, yarn (CI matrix above) |
| Frontend / TanStack Start | TanStack Router/Start, React Router, Next, Nuxt, Svelte, Solid, Astro, React Native ([schemas.ts](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/packages/types/src/schemas.ts)) | Next.js only | Next, Vite, Start, React Router, Astro starters |
| Backend / Hono | Hono, Express, Fastify, Elysia, Convex, "self" | Next route handlers | n/a |
| UI library | shadcn only, as a shared `packages/ui` using the `base-lyra` style (Base UI) ([components.json.hbs](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/packages/template-generator/templates/packages/ui/components.json.hbs)) | Tailwind toggle | Radix, Base UI, React Aria |
| Auth | Better Auth, Clerk | NextAuth, Better Auth | n/a |
| Addons | Turborepo, Nx, Biome, Husky, Lefthook, Oxlint, Ultracite, PWA, Tauri, MCP, Skills… ([README](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/README.md)) | ESLint or Biome | Turborepo (with `--monorepo`) |

None of them offers access-code auth, a launcher or subdomain routing, or a way to add a second app with platform wiring. robkit's `robkit add` is new ground. The BTS `add` tests show what the hard cases are: keeping the user's workspace settings and JSONC comments, rejecting a corrupt config, and refusing names that look like paths ([add-project.test.ts](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/apps/cli/test/add-project.test.ts)).

## 5. Licence, maintenance, building on one

**Licence and maintenance:**
- **Licence:** all three are MIT ([BTS](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/LICENSE), [T3](https://github.com/t3-oss/create-t3-app/blob/4709861/LICENSE), [shadcn](https://github.com/shadcn-ui/ui/blob/96da9cc/LICENSE.md)).
- **Better-T-Stack activity:** 135 commits between 2026-07-28 and 2026-10-28, with releases 3.46 to 3.49 in October.
- **shadcn activity:** 280 commits in the same window.
- **create-t3-app activity:** the last commit on `main` was 2025-12-13, a security bump to React and Next. These counts come from `git log` on the clones. The [create-t3-turbo](https://github.com/t3-oss/create-t3-turbo) template was also last touched in December 2025.

**Options for building on one:**
- **Fork BTS: no.** Its engine is typed to BTS's own `ProjectConfig`, and every handler hard-codes BTS's folder layout (`apps/web`, `apps/server`) and dimensions ([generator.ts](https://github.com/AmanVarshney01/create-better-t-stack/blob/a9bd456/packages/template-generator/src/generator.ts)). robkit's point is a platform, with a hub, guard adapters and the ability to add apps later, so we would rewrite most of it. We would also inherit about 20 addon dimensions that we don't want.
- **Use BTS's published template-generator as a library: no.** It isn't generic for the same reason.
- **Fork T3: no.** It is dormant, covers Next only, and its copy-per-combination design grows badly.
- **Ship robkit's stack templates as a shadcn registry: not as the main path.** A `registry:item` can carry arbitrary files with `~/` targets, dependencies and env vars ([docs](https://ui.shadcn.com/docs/registry/registry-item-json)), and any GitHub repo can serve as a registry ([github docs](https://ui.shadcn.com/docs/registry/github)). The limits:
  - Items have no conditional logic per option, so we would need one item per package manager or UI combination.
  - The CLI needs a `components.json` and resolves paths from it.
  - It writes plain version ranges. Robnet's own CLAUDE.md records that `shadcn add` replaces `catalog:` with caret ranges and rewrites `pnpm-workspace.yaml`. I found no pnpm-catalog handling in the shadcn dependency updater ([update-dependencies.ts](https://github.com/shadcn-ui/ui/blob/96da9cc/packages/registry/src/updaters/update-dependencies.ts)).
  - It can't register a subdomain, a DB schema or a manifest in the hub.

**Recommendation:** build a small generator of our own. robnet already has the seed: a plop/`turbo gen` generator with Handlebars templates (`tooling/generators/turbo/generators/config.ts`). Take these from prior art:
1. **From BTS:** one template folder per dimension (`stack/`, `ui/`, `pm/`, `devtools/`), layered into a virtual FS. Use ts-morph or JSON processors for edits that cross options, instead of T3-style copy-per-combination files.
2. **From BTS:** a `robkit.json` written at init with the choices and the CLI version, read by `robkit add`.
3. **From BTS's three tiers and shadcn's template matrix:** a compatibility-oracle unit suite, plus a sharded CI job that installs, typechecks, builds and boots a curated set covering every stack × every package manager at least once. Run it on a daily cron, so that a dependency drifting upstream fails our build before it fails a user.
4. **Platform code (guard, session, adapters, ui tokens) in versioned npm packages.** The generated app then holds only thin glue, and an update is a dependency bump. No CLI here gives a better update path than shadcn's per-file `--diff`.
5. **shadcn for the UI choice:** for the shadcn-family kits (Radix, Base UI, React Aria), have init run `shadcn init --base <radix|base|aria>` against our `packages/ui` rather than templating them ourselves. Chakra and other kits get a plain template layer. A robkit shadcn registry for launcher and admin blocks can come later.
