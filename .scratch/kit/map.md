# Map: robkit v0.1

## Destination

A decided spec and ordered PR list for robkit v0.1. `npm create robkit` scaffolds a monorepo with the platform (Hono core, a React hub with access-code login, admin, shared Postgres). `robkit add` opens a selector of stack templates (v0.1: TanStack Start, and React with Hono) and drops in an app that already has auth, a database schema and a subdomain. All of it runs locally with one command. Deploys use R's existing Coolify method for now.

## Notes

- **Product:** painless self-hosting of small, often vibe-coded, apps for friends and family. Auth, database, routing and the launcher come built in. The templates are stacks, not R's apps. robkit is a self-hosting cookbook shared with the community, so the init options are part of the product; R's own suite of apps will be a fork of this repo.
- **Reference, not base:** `C:\Users\rober\code\robnet` (to be renamed `robnet_inspiration`). Borrow its ideas (guard outcome table, access codes and intro links, launcher, admin settings, ui tokens), not its Start-specific glue.
- **Architecture draft:** the Robnet Platform docs site (https://claude.ai/artifact/Ps4buZoTFDtdaDZycwcP68): a framework-free core on web Request/Response, one server adapter per stack, plus client adapters.
- **Domain:** robkit.dev, for testing once the kit works locally.
- **Skills:** grilling and domain-modeling for every grilling ticket. Ask R one question at a time on a decision card.
- **Appetite:** radical choices welcome, nothing for its own sake. The goal is a repo a reader finds slick and clean.

Superseded by [app-sharing ticket 01](../app-sharing/issues/01-one-opinionated-stack.md): the hub and admin always draw with shadcn on Base UI (2026-11-05).
- [What is robkit's domain glossary?](issues/03-domain-glossary.md): 20 terms in `GLOSSARY.md`; hub (login and launcher UI) and core (Hono backend) are distinct; one owner per install, claimed on first run (the Coolify model), everyone else a guest; roles, not grants.

- **The owner claims the install and signs in** (build ticket 03, R, 2026-11-01): the setup screen stays open with no one-time token, as in Coolify, so the owner claims a hosted install as soon as it's up. Core generates its Ed25519 key on first boot and keeps the private half in its own schema, not in env. The default `ROBKIT_DOMAIN` becomes `robkit.localhost`, because Chromium and Firefox reject a `Domain=localhost` cookie; this replaces the `localhost` default in the CLI-flow and local-dev decisions, and the `test` code works while the domain ends in `.localhost`.
- **A guarded example app** (build ticket 04, chosen in the build, awaiting R's review): apps get core's public origin as `ROBKIT_CORE_URL` rather than reading it from the request. `/refresh` always returns to the app, and the app's guard decides about login. Requests that aren't page loads get 401 JSON instead of a redirect.
- **Guests sign in with codes** (build ticket 05, R, 2026-11-01): core stores access codes as plain text, so admin can show a code and its intro link at any time. A code may have an expiry, and an expired code ends its sessions at the next refresh, as a revoked one does. Chosen in the build, awaiting R's review: a guest's token names the code's id rather than the code, and admin is a Hono server guarded as owner-only, so a guest gets a real 404.
- **Roles gate apps** (build ticket 06, R, 2026-11-01): core holds each app's access rule in its app catalog and serves it at `GET /apps/<slug>/access`, and adapters cache it for 60 seconds. The dev runner hands core the app list as `ROBKIT_APPS`, and core adds a new app as owner-only without overwriting the owner's edits. The CI journey re-gates the example app and waits out the cache rather than adding a second app. Chosen in the build, awaiting R's review: a guest's token carries role ids, core reissues it as soon as their roles change, each app learns its slug from `ROBKIT_APP`, and an open launcher asks core again every 30 seconds.
- **TanStack Start passes the same checks** (build ticket 07, chosen in the build, awaiting R's review): both adapters run one `requestGuard` from `@robkit/session` on web-standard requests. The Start adapter wraps the app's server entry rather than sitting in `src/start.ts`, which Start also loads in the browser, and hands routes and server functions the viewer as request context. The guard marks its 401 with a `Robkit-Session` header, and `@robkit/react`'s `sessionFetch` acts only on that, navigating once and coming back to the current page. App slugs can't contain hyphens, since each slug is a Postgres role, so the Start example is `start`.
- **The generator writes the default install** (build ticket 08, chosen in the build, awaiting R's review): the hand-built apps became template layers in `packages/create-robkit`, merged in memory with manifests deep-merged. The generator writes an install's catalog from robkit's own, and `--link` points `@robkit/*` at a checkout through pnpm overrides. An install has one root ESLint config, its unit tests ship before Vitest becomes a choice, and the whole-stack test runs on generated installs.
- **The init wizard** (build ticket 09, chosen in the build, awaiting R's review): init asks its questions when no choice flag is given, offers the options a later ticket adds as "coming later", and prints the flags that make the same install. The UI kit question is No or a disabled Yes until a kit lands. Installing and `git init` are one question, and opt-in as `--install` on flags. Superseded by [app-sharing ticket 01](../app-sharing/issues/01-one-opinionated-stack.md): the wizard asks the folder and the example's stack, and installing is the `--install` flag only (2026-11-05).
- **Architecture review** (R, 2026-11-03): eight refactors become build tickets 22 to 29, built before the tickets that lean on them. Tickets 10, 11, 15 and 18 now wait for them. The refactors cover: app slugs, a provision step, init as one operation and one table of its choices, core's HTTP layer, the guard's own tests and its contract with `sessionFetch`, the install's addresses, and how the hub and admin call core.
- **App slugs are checked at start** (build ticket 22, chosen in the build, awaiting R's review): the slug rule is `slugProblem` in `@robkit/dev`, which returns why a name can't be a slug, or nothing. Finding the apps and provisioning a database both call it, and `robkit add` can use it as a prompt's validator. `pnpm dev` checks every folder under `apps/` that has a `package.json` and exits before Compose starts if one fails. A folder without a `package.json` isn't an app and isn't checked.
- **Provisioning is its own step** (build ticket 23, chosen in the build, awaiting R's review): `provisionApps` in `@robkit/dev` gives each app with a `migrate` script its schema and role and then runs the script, with no proxy or app running. It takes the install's folder and finds the apps itself. `pnpm dev` runs it after Postgres starts, and a second run changes nothing but the passwords.
- **Init is one operation** (build ticket 24, chosen in the build, awaiting R's review): `init(choices, dir, { install, link })` in `create-robkit` generates, writes, and with `install` installs dependencies and initialises git. The command line and the whole-stack test both call it, so CI's installs are git repositories like a user's. `install` stays one switch for both, matching the wizard's one question.
- **One table of init's choices** (build ticket 25, chosen in the build, awaiting R's review): `choiceTable` in `create-robkit` describes each choice once, with its flag, question, options, labels, "coming later" options and each option's template layer. The flag parser, usage text, wizard and generator read it, so an option is one table entry plus its folder. The UI kit gets a `--ui-kit` flag, which takes only `none` until a kit lands. Superseded by [app-sharing ticket 01](../app-sharing/issues/01-one-opinionated-stack.md): with one choice left, the table became a plain list of stacks (2026-11-05).
- **Core's routes and rules** (build ticket 26, chosen in the build, awaiting R's review): one `viewer` middleware in core reads and renews the session for every route that needs the viewer, and each owner route names the owner gate itself. Each input rule sits with the code that stores its data, as a `read…(fields)` that returns the value or `{ error }`; claiming the install moved to `owner.ts`.
- **The guard's own tests and its contract with `sessionFetch`** (build ticket 27, chosen in the build, awaiting R's review): `requestGuard` is tested on its own against a shared fake core, and the adapters' tests keep only the conformance table and their glue. The guard's 401 for a call lives in `@robkit/session/lapsed`, which the guard writes and `sessionFetch` reads. It leaves `next` out, and the page adds its own URL. `coreKeys`, `coreAccess` and the `keys` option are no longer public.
- **The install's addresses** (build ticket 28, chosen in the build, awaiting R's review): `@robkit/session/addresses` is the one place that turns an install's domain into addresses. `install({ domain, protocol, port })` gives each app's host and origin and checks a `next` URL, `installAt` finds the install from core's or the hub's address, and `platformApps` names core, the hub and admin. It lives in `@robkit/session` because the hub, admin, core and the dev runner may all import it under the layer rule. The fake core states its hub origin as a literal rather than importing it, since `@robkit/session`'s own tests import the fake core.
- **The hub and admin call core one way** (build ticket 29, chosen in the build, awaiting R's review): `callCore` in the install's own `packages/core-client` is the one way the hub and admin call core, with one result shape, `{ ok, value }` or `{ ok, error }`. It sits in the `base` layer, so every UI kit's hub and admin share it. Their tests answer from its `fakeCore` and check what each call returns.
- **Slugs and production passwords** (R, 2026-11-03, ticket 10's open questions): a slug is lowercase letters and digits, starting with a letter, so it's a valid hostname label and a plain Postgres identifier. In production each app's role password is an HMAC of its slug under one install secret, `ROBKIT_DB_SECRET`, held only by the provision step, and robkit prints each app's `DATABASE_URL` for the owner to set once on the host. Ticket 11 builds the derivation.
- **`robkit add`** (build ticket 10, chosen in the build, awaiting R's review): `create-robkit` ships a second command, `robkit`, which an install runs as `pnpm robkit add`. It writes `apps/<slug>` from a stack `robkit.json` enables, or from the install's own `robkit/templates/<stack>`, which replaces it whole, and writes files only. An app's manifest is the `robkit` field of its `package.json`: who may open it, with roles named, and an emoji. The dev runner hands core every manifest as JSON in `ROBKIT_APPS`; core adds a new app with its declared rule, creating any role it names, and keeps the owner's rule after that. The launcher shows the icon. With no flags `add` asks its questions and prints the flags that skip them. The generator catalogs every enabled stack's dependencies, so an added app needs no new versions. Every install now offers every stack, after [app-sharing ticket 01](../app-sharing/issues/01-one-opinionated-stack.md) (2026-11-05).
- **Agent files and the layer rule** (build ticket 12, chosen in the build, awaiting R's review): an install's layer rule is the ticket's three rules, and `robkit check` is its only implementation. It reads each app's files with TypeScript's parser, so it holds without ESLint, and the install's `lint` script runs it. The root `AGENTS.md` states the rule word for word, each app's `AGENTS.md` covers its stack and ends with its ORM's section, and each `CLAUDE.md` imports its `AGENTS.md`. Every install has a CI workflow that lints, typechecks, tests and builds.
- **The hosted install** (build ticket 11, chosen in the build, awaiting R's review; the live deploy waits for R): every app runs from the install's one `Dockerfile`, built with `turbo prune` and a frozen install, with `ROBKIT_APP` as its build argument. Each container migrates its app's database as it starts, and core's first runs the provision step, whose passwords are the HMAC of each slug under `ROBKIT_DB_SECRET`. `pnpm robkit database-urls` prints each app's `DATABASE_URL` for the owner to set once as a shared variable on Coolify. `pnpm robkit deploy` creates or adopts each app's Coolify application, sets its variables, and deploys core first, then each changed or new app; the install's CI runs it on every push to `main`. The `@robkit/*` packages ship JS in `dist`, and until they're on npm `pnpm robkit vendor` packs them into the install. `pnpm test:production` in `tooling/e2e` proves the install end to end behind Caddy TLS on `robkit.test`. The runbook is the install's `docs/deploy.md`.
- **Prisma** (build ticket 13, chosen in the build, awaiting R's review): an ORM is a template layer, `orms/<orm>/app`, laid over every app, and the example apps now query with Drizzle, so the ORM choice is real. Prisma 7 keeps each app's tables in the schema named after its slug, through `prisma.config.ts` and the adapter. Its generated client is committed, and `pnpm db:migration` diffs the local schema into the next migration, since a diff from empty creates the schema, which the app's role may not. An option names the dependencies whose install scripts it needs as `builds`, which become pnpm's `allowBuilds`. Superseded by [app-sharing ticket 01](../app-sharing/issues/01-one-opinionated-stack.md), which removed Prisma and the ORM choice (2026-11-05).
- **Kysely** (build ticket 14, chosen in the build, awaiting R's review): Kysely's layer writes its migrations as code listed in `src/migrations/index.ts`, and its migrator keeps its tables in the role's own schema, found with `current_schema()`, because it otherwise finds another Kysely app's tables by name. Superseded by [app-sharing ticket 01](../app-sharing/issues/01-one-opinionated-stack.md), which removed Kysely (2026-11-05).
- **The UI kit layer, with shadcn on Base UI** (build ticket 15, chosen in the build, awaiting R's review): the install's tokens are shadcn's variables in `packages/theme/theme.css`, the only file that sets them, and the no-kit hub and admin draw with Tailwind classes named after them. A kit replaces only the hub's and admin's `ui.tsx`, the seam their screens draw every control through, and adds `packages/ui`. Init doesn't run the shadcn CLI: the kit is shadcn's output committed as a template layer, which `pnpm --filter create-robkit shadcn-kit` regenerates, so init stays offline and stable. The example app uses the kit, and `robkit add` does unless `--no-ui-kit`. axe checks every install's pages in the whole-stack test. The opt-out is superseded by [app-sharing ticket 01](../app-sharing/issues/01-one-opinionated-stack.md): every install and app has the kit, and its layers are plain files (2026-11-05).
- **shadcn on Radix** (build ticket 16, chosen in the build, awaiting R's review): `--ui-kit shadcn-radix` is the shadcn CLI's `--base radix` output, regenerated by the same script, with `radix-ui` in place of Base UI and the same theme tokens. The hub's and admin's controls are the Base UI kit's, but admin's checkbox maps Radix's "indeterminate" to unchecked. Both shadcn kits share one app layer, `ui-kits/shadcn/app`. The Prisma install carries the kit in the whole-stack test and runs the role journey on it. Superseded by [app-sharing ticket 01](../app-sharing/issues/01-one-opinionated-stack.md), which removed shadcn on Radix (2026-11-05).
- **Chakra** (build ticket 17, chosen in the build, awaiting R's review): `--ui-kit chakra` is a hand-written `packages/ui` that re-exports Chakra 3 with a `Provider` and a theme whose every colour, radius and font names a variable in `theme.css`. Tailwind stays for layout, so the screens don't change. Each `ui.tsx` gains `Root`, which wraps the page, for a kit that needs a provider. Chakra's layers resolve modules as a bundler would, its hidden checkbox and radio inputs lie over their labels, and its cascade layers are off, since an empty one broke server-rendered CSS. The React + Hono install carries it in the whole-stack test, and the Prisma install in production. A theme journey in every install checks the theme's variables restyle each kit the same way. Superseded by [app-sharing ticket 01](../app-sharing/issues/01-one-opinionated-stack.md), which removed Chakra and `Root` (2026-11-05).
- **The package manager table, with bun** (build ticket 18, chosen in the build, awaiting R's review): everything that differs per package manager is one entry in `packageManagers`: its settings file and shape, lockfile, install and run commands, and how the templates' pnpm commands are spelled for it. The templates stay written for pnpm, and the generator and `robkit add` spell them for the install's manager. bun keeps its catalog, overrides and trusted install scripts in `package.json` and its minimum release age in `bunfig.toml`, and always runs scripts as `bun run`. The dev runner runs the manager the install's `packageManager` names. Each manager's layer brings its own Dockerfile, none using Corepack. The whole-stack and production Kysely installs run on bun. Superseded by [app-sharing ticket 01](../app-sharing/issues/01-one-opinionated-stack.md), which removed bun and the table (2026-11-05).
- **yarn** (build ticket 19, chosen in the build, awaiting R's review): yarn 4 is the third entry in the package manager table. Its catalog sits in `.yarnrc.yml`, and its builds and `--link` overrides in `package.json` as `dependenciesMeta` and `resolutions`, so a manager's settings may span files. It installs into `node_modules`, never PnP, refuses versions under a day old, and runs only the install scripts the choice table allows. The Dockerfile and CI install yarn with npm at the version `packageManager` names, replacing the image's Yarn 1, so nothing needs Corepack. With `--link`, yarn takes robkit's packages through `portal:`, so their bins link. The whole-stack Prisma install runs on yarn. A yarn install deploys once the packages are on npm (ticket 31), since turbo can't prune a yarn lockfile that takes them from vendored tarballs. A test serves them from a local registry and checks the prune and frozen install. Superseded by [app-sharing ticket 01](../app-sharing/issues/01-one-opinionated-stack.md), which removed Yarn (2026-11-05).
- **Dev tool options** (build ticket 20, chosen in the build, awaiting R's review): every dev tool is ready. ESLint + Prettier and Vitest are on by default; Playwright and Husky + lint-staged are opt-in. The templates keep each test beside its code, so an install without Vitest leaves the tests and their runner out. Playwright adds `tooling/e2e`, whose `pnpm test:e2e` runs the install's own `pnpm dev` on ports and a database of its own, and each CI workflow runs it when that folder exists. Husky sets up its pre-commit hook from a root `postinstall`, which every package manager runs, and its hook runs `robkit check`, plus ESLint and Prettier on the staged files when the install has them, through a layer a tool lays only beside another. init now runs `git init` before installing, so the hook is set up at once. Each tool adds a line to the install's root `AGENTS.md`. Superseded by [app-sharing ticket 01](../app-sharing/issues/01-one-opinionated-stack.md): every install has ESLint with Prettier, Vitest and Husky, and Playwright is gone (2026-11-05).
- **CI passes reliably** (build ticket 34, chosen in the build, awaiting R's review): about 4 in 10 CI runs failed on a journey whose page never drew. On CI's runner Docker runs natively, so every compose project's network adds and removes host interfaces, and Chromium fails its in-flight requests with `ERR_NETWORK_CHANGED`. CI now puts every test Postgres on the host's network through `COMPOSE_FILE`, which reaches `pnpm dev`, the runner tests and `@internal/test-postgres`. Failed journeys print what the browser saw. `verifyPassword` now refuses only a hash it can't read, and lets any other scrypt failure throw, so the right password is never refused.
- **Kit matrix CI** (build ticket 21, chosen in the build, awaiting R's review): `@internal/matrix` plans the matrix from init's choice table. Each pull request runs a pairwise set of 14 generated installs and each night all 72, one GitHub job each, named by the init flags that make it. Each job adds an app on the second stack and runs the install's own CI steps on a clean `PATH`. No combination may fail, and the `Every combination` job is the check to require once `main` has branch protection. The browser journeys stay in the whole-stack test, once per stack and once per kit. Superseded by [app-sharing ticket 01](../app-sharing/issues/01-one-opinionated-stack.md), which removed the matrix (2026-11-05).
- **Slim production images** (build ticket 32, chosen in the build, awaiting R's review): each Dockerfile builds the app, then deletes every `node_modules` and installs only that app's production dependencies, and runs it on node:24-alpine with npm, Yarn and Corepack removed. An app's `dependencies` are what its server imports, and what Vite bundles is a dev dependency, so the hub's and admin's React, theme and UI kit moved there. `test:production` fails on any package in an image the app doesn't reach through its production dependencies. The hub and admin images halved; core and the Start examples didn't, because Node, TanStack Start's toolchain and Prisma's CLI stay, and ticket 35 weighs what could go next.
- **The full gate passes on a dev machine** (build ticket 36, chosen in the build, awaiting R's review): in WSL with Docker Desktop the gate had stopped passing in one run, origin/main included. Test Postgres syncs stalled the shared disk (IO pressure up to 38%), Docker's daemon with it, and Postgres containers ran out of health checks. Test Postgres data now stays in memory, the health check has a two-minute start period and runs every 10 seconds once up, Postgres ports skip the ones Docker already publishes, and a detached watcher removes what a killed test left, by Compose project and by an inherited `ROBKIT_TEST_TAG`.
- **The production e2e runs in CI** (build ticket 33, chosen in the build, awaiting R's review): `production.yml` deploys each production install in its own job on every push to `main`, nightly, and on pull requests labelled `production`, with image layers kept in GitHub's BuildKit cache, one scope per install and app. A rerun takes about 3 minutes per install instead of 5 to 7. Each journey's browser opens only once the host's interfaces stop changing, and the apps can now read Caddy's root certificate whatever uid runs the test. With one install left, [app-sharing ticket 01](../app-sharing/issues/01-one-opinionated-stack.md) made it one job, with one cache scope per app (2026-11-05).
- **The sign-in limit sees each visitor behind a tunnel** (build ticket 30, chosen in the build, awaiting R's review): with `ROBKIT_TRUSTED_PROXY=cloudflare`, which `robkit deploy` sets on core from `coolify.json`'s `trustedProxy`, core names each visitor by `CF-Connecting-IP`, and requests without it share one limit. Otherwise it keeps the last `X-Forwarded-For` entry, so local dev is unchanged. The setting is safe only when nothing but the tunnel reaches the host, which the install's deploy runbook says. The production e2e's Caddy now stands in for Cloudflare and the tunnel's hop into Traefik.
- **App sharing** (R, 2026-11-05): sharing apps between installs is at robkit's heart. One opinionated stack (pnpm, Drizzle, shadcn on Base UI, ESLint with Prettier, Husky, Vitest), per-app session tokens, then two sharing approaches built side by side for R to pick from. See the [App sharing PRD](../app-sharing/PRD.md).
- **One opinionated stack** (app-sharing ticket 01, R, 2026-11-05; chosen in the build, awaiting R's review): every install has pnpm, Drizzle, shadcn on Base UI, ESLint with Prettier, Husky with lint-staged, and Vitest, and the other options are deleted outright. Every install offers both stacks, and `robkit add` defaults to Start. Init asks only for the folder and the example app's stack, which `--stack` also gives and `robkit.json` records as `exampleStack`. Installing is `--install` only, and the checkout's `pnpm create-install` passes it. The templates are plain folders, `base` and one per stack, so every install of one robkit version has the same `packages/ui`, `packages/theme`, `packages/core-client` and catalog. The whole-stack test runs two installs, one with its example on each stack, each adding an app on the other; the production e2e runs the default install.
- **Per-app session tokens** (app-sharing ticket 02, R, 2026-11-05; chosen in the build, awaiting R's review): no cookie goes on the parent domain. Core's token has the audience `core` and sits in a host-only cookie on `core.<domain>`, and core reads no other. Each app, admin included, holds its own token, with its slug as the audience and no session id, in a host-only cookie on its own host, and its guard accepts no other. An app with no token of its own sends a page load to core's `/refresh` with a random state it keeps in a cookie. Core reads only its own cookie and sends the browser to the app's `/_robkit/session` with a token for that app, or none if nobody is signed in, and the app's guard checks the state, keeps the token, or core's word that nobody is signed in for a minute, and decides about login as before. A call whose token lapsed goes through the app's `/_robkit/refresh`. The callback answers a page instead of redirecting when it can't go on, which also ends the old redirect loop for an app whose clock runs ahead of core's. See [the ticket](../app-sharing/issues/02-per-app-tokens.md).
- **React + Express** (stacks ticket 01, after [the stacks PRD](../stacks/PRD.md), R, 2026-11-07; chosen in the build, awaiting R's review): `express` is a ready stack. `@robkit/express` is Express 5 middleware that runs `requestGuard` and hands handlers the viewer on `res.locals`, typed through `GuardedResponse`. It reads only the URL and headers, so a body parser can sit after it, and answers 400 to an HTTP/1.0 request with no Host. The template follows react-hono's; in dev a Vite plugin hands Express every request Vite doesn't answer itself. What a stack knows lives in its adapter, its template folder and its whole-stack test file, `tooling/e2e/src/<stack>.test.ts`, which a repo check requires for every ready stack. The rest follows `readyStacks`: the whole-stack test makes an install per stack, each adds an app on the next stack and runs its own CI workflow, and the production test adds an app on every stack but the example's. create-robkit's README lists what adding a stack takes. See [the ticket](../stacks/issues/01-react-express.md).
- **Next.js** (stacks ticket 02, chosen in the build, awaiting R's review): `next` is a ready stack, on Next 16.4.5 with the App Router. `@robkit/next`'s `guarded(options)` is the app's `src/proxy.ts` export, which Next runs on Node before every path but `/_next/`. It hands the app the viewer in a `robkit-viewer` request header that starts with a random key the server process made, so a header a client sends is replaced, and a forged one on a path the proxy skips fails the key check. Server components, route handlers and server actions read it with `await viewer()`, which throws a fault naming `src/proxy.ts` when the proxy didn't run. A client navigation that meets the guard's 401 falls back to a full page load, so it takes the page-load bounce with nothing added. A server action's 401 also carries `x-action-redirect`, so Next's client follows the 401's location (core's refresh or the hub's sign-in) with `next` set to the page. The build goes to `dist`. Telemetry is off, set by the `dev` script for `next dev` and by `next.config.ts` for the build and the server. The install's pnpm settings override styled-jsx's optional Babel peer, which would otherwise ship Babel in the image. And `node --run start` migrates and then serves with `next({ dev: false })` from `src/serve.ts`. See [the ticket](../stacks/issues/02-next.md).
- **React + Go** (stacks ticket 03, after [the stacks PRD](../stacks/PRD.md), R, 2026-11-07; chosen in the build, awaiting R's review): `go` is a ready stack. Its guard is the Go module `github.com/RobertScholey98/robkit/go` in `go/`, a port of `@robkit/guard` and `requestGuard` to Go's standard library, as `http.Handler` middleware with `session.ViewerFrom`, tested against `conformance.json` and a ported fake core ([ADR 0013](../../docs/adr/0013-go-guard-is-a-port.md)). The app owns its database: pgx and SQL migrations embedded in the binary, which the stack table says with `ownsDatabase`. In dev the Go server listens on `PORT` and proxies the page and Vite's HMR to Vite on a free port; in production it serves `dist/public` with an `index.html` fallback. Its `go.mod` reaches the module by `replace`: the checkout under `--link`, `vendor/robkit/go` otherwise, which `robkit vendor` fills. The Dockerfile fetches Go only for an app with a `go.mod`, the install's CI sets Go up the same way, `robkit check` scans `.go` files, and `pnpm dev`, init and `robkit add` say how to install Go when it's missing. See [the ticket](../stacks/issues/03-react-go.md).

## Known gaps

Left open by build tickets 02 to 11 and app-sharing ticket 02, with no ticket yet:

- For up to a minute after the owner changes an app's rule, the launcher and the app can disagree. (06)
- Roles can't be renamed or deleted, and an app's name is its slug. (06)
- The sign-in limit is soft: two attempts racing in parallel can both get past the check. (03)
- Local dev doesn't work in Safari, because WebKit doesn't send the cookie on the hub's fetch to core. Tested in Playwright's WebKit only. (03)
- In dev, React StrictMode sends an intro link's sign-in twice, which leaves one extra session. (05)
- Vite prints `http://127.0.0.1:<port>`, which shows nothing, since each app answers only on its subdomain. (02)
- Running `pnpm install` anywhere on the machine touches the hard-linked files under a running core, and `node --watch` restarts it. (08)
- `pnpm dev`, the runner tests, the whole-stack test, `repo-checks` and one `migrate.test.ts` case need Linux or macOS. The whole suite passes in WSL. (04 to 09)
- In production, apps reach core over its public URL, through Cloudflare and back, not over Coolify's Docker network. (11)
- Any container on Coolify's network can reach core directly and send its own `X-Forwarded-For` or `CF-Connecting-IP`. Only the owner's apps run there. (30)
- After sign-out, an app the browser opened in the last 15 minutes still lets it in until that app's token expires, since apps verify tokens locally and core can't clear another host's cookie. Core's session ends at once, so the hub, admin's calls to core and every refresh see the browser signed out. (app-sharing 02)
- An app open to anyone takes core's word that nobody is signed in for a minute. A visitor who opens it signed out, then signs in at the hub, shows as nobody there until that minute is up. (app-sharing 02)
- Core hands an app its token in the callback's URL, so a proxy that logs URLs logs that app's token, good for 15 minutes on that app alone. (app-sharing 02)
- A browser that keeps no cookies used to see an app open to anyone as nobody. It now stops at the app's callback with a page saying it kept no cookie. (app-sharing 02)
- Any app can send a visiting browser through core's `/refresh` and learn who the visitor is: their id, kind and roles. That is what an app needs to serve them, but an imported app learns it too, for every guest who opens it. (app-sharing 02)
- A browser that signed in before per-app tokens keeps the old parent-domain cookie until it expires, up to 30 days. Core and every app ignore it, but it still reaches every app's server. (app-sharing 02)
