# 07: TanStack Start passes the same checks

**What to build:** A TanStack Start example app runs behind the Start adapter and behaves exactly like the Hono one: the same redirect to login and back, the same `/refresh` bounce, and the same access decisions, because both adapters run the shared conformance cases. Server functions receive the verified viewer from a middleware rather than re-reading the request.

## Comments

Notes from the build, for ticket 08 onwards. R hasn't reviewed the choices marked "chosen in the build" yet.

- **Shared request guard.** `requestGuard` in `@robkit/session` runs the guard on a web-standard `Request`: it reads the cookie, verifies the token, loads the rule with `coreAccess`, and answers with a redirect, a 401, a 404 or a 503. Both adapters are now a few lines over it, so a third stack only maps its framework onto `Request` and `Response`.
- **Start adapter (chosen in the build).** `guarded(entry, options)` wraps Start's server entry in `src/server.ts` and hands Start the viewer as its request context. The app registers that context once (`declare module "@tanstack/react-start"`), then routes and server functions read `context.viewer`. The ticket says "a middleware". A Start request middleware would have to sit in `src/start.ts`, which Start also bundles for the browser, so the guard's server code would ship to the client. The entry is the server-only seam.
- **The guard's 401 (chosen in the build).** A request that isn't a page load still gets 401 JSON `{ error, location }`, now with a `Robkit-Session: login | refresh` header. The header is how the page tells the guard's 401 from the app's own.
- **Client helper (chosen in the build).** `@robkit/react` exports `sessionFetch`, a `fetch` for calls from the page. On the guard's 401 it sends the browser to the location, with `next` set to the current page, because the adapter only knows the URL that was called. It navigates once however many calls fail, and those calls never settle, so callers don't flash an error as the page leaves. A page restored from the back-forward cache can navigate again. Every other answer, errors included, goes to the caller untouched. Start apps wire it in with `createStart(() => ({ serverFns: { fetch: sessionFetch } }))`. Without it, Start's client returns the guard's 401 JSON as if it were the server function's result. The package has no React code yet.
- **Example app.** `apps/start` mirrors `apps/example`: same heading, viewer id and visit count, plus a "Visit again" button that calls a server function. Its slug is `start`, not `start-example`, because the runner makes each slug a Postgres role, and role names take no hyphens. Ticket 10's `robkit add` must refuse such names or map them. `src/routeTree.gen.ts` is generated by TanStack Router and committed so `tsc` works before a first `vite dev`. ESLint and Prettier skip it, and `addExtensions` keeps its imports' `.tsx` extensions.
- **CI journey.** The owner journey runs on both examples, a guest gets the same 404 from both, and the role journey gates both apps together, so they share the rule-cache waits. A new journey calls the Start app's server function with an expired token and checks the bounce through core's `/refresh` and back. The whole-stack test still takes about two and a quarter minutes.
- **Still open.** The Start app runs under `vite dev` only. Ticket 11 needs a production server for Start's `dist/server/server.js`.
- **Tests on Windows.** Same as 05 and 06. Natively, `pnpm dev` fails with `spawn pnpm ENOENT`, and the catalog repo check fails on `main` too. The whole suite passes in WSL Ubuntu 22.04, run from an archive of the branch.
