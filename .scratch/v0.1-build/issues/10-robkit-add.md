# 10: `robkit add`

**What to build:** In an install, `robkit add` offers only the generators enabled in `robkit.json` and asks for the name, who can open it (anyone, roles, owner only), the UI kit opt-in when relevant, and an icon. It writes `apps/<slug>` and the app's manifest. After `pnpm dev`, the new app opens at `<slug>.robkit.localhost`, gated as chosen.

**Blocked by:** 08, 22, 23, 25

**Status:** needs-info

**Provisioning (draft, for R to react to):** `add` writes files only and creates nothing in Postgres. A provision step reads every app's manifest, creates any missing schema and role, and registers the app with the launcher. It is safe to run any number of times. It runs before migrations, under `pnpm dev` locally and as a pre-deploy step in production, so a hosted install gets a new app on its next deploy the same way a laptop does. It is the only step that holds a Postgres admin connection.

- [ ] Both stacks can be added, and each passes the guest journey
- [ ] The new app's role can only touch its own schema
- [ ] Running the provision step twice changes nothing the second time
- [ ] The new app's migrate step runs after provisioning and before the app starts
- [ ] A `robkit/templates/<stack>` folder in the install overrides that stack's template
- [ ] `robkit add` with flags works without prompts

**Open:**

- Where each app's role password comes from in production: generated by the provision step and handed to the app's env, or set by the owner on the host.
- Whether slugs may keep underscores. The slug rule allows `_`, but a slug is also a subdomain, and `my_app.<domain>` isn't a valid hostname under RFC 1123. Some certificate authorities refuse it. `add` reuses the rule from `@robkit/dev` (ticket 22), so a change there covers both. (Raised in review of ticket 22.)

Source: the robkit v0.1 spec, https://claude.ai/artifact/MrC9JDG3NK2tSw7h6x2VV5

## Comments

Notes carried over from the finished tickets 02 to 09, which were deleted once done:

- **Slugs.** Each slug becomes a Postgres role, so it must match `^[a-z][a-z0-9_]{0,62}$`, and a name with a hyphen can't have a database. `robkit add` must refuse such names or map them. That's why the Start example's slug is `start`, not `start-example`. (02, 07)
- **Mounting a stack.** A stack's Vite config reads its host from `ROBKIT_APP`, so a stack template names no slug and `add` can mount it at any slug. (08)
- **Drizzle migrations.** An app's role can't run Drizzle's stock migrator, because it starts with `CREATE SCHEMA IF NOT EXISTS`, which Postgres refuses to a role without CREATE on the database. `@robkit/core`'s `migrate` skips that statement. Every Drizzle app template needs the same. (02)
- **Platform apps.** Core's app catalog doesn't hold the hub or admin. Admin passes a fixed owner-only rule to its guard. (06)
