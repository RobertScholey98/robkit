# 06: No app can be framed from another origin

**What to build:** Nothing in an install tells a browser who may frame a page, so an imported app can put `admin.<domain>`, or any other app, in a frame. The frame is same-site, so the viewer's cookies go with it, and two tricked clicks in a framed admin open an app to everyone ([review](../research/review-2026-11-09.md), "A sibling app can frame admin"). Every adapter owns the path an answer takes, so the guard can send the header for every guarded app, admin included, from a package that updates.

- **The guard sends `X-Frame-Options: SAMEORIGIN`.** And `X-Content-Type-Options: nosniff`. Both go on every answer the guard lets through, and on the guard's own pages.
- **No framing header on a redirect of the guard's or of core's.** Those carry `nosniff` alone. A redirect renders nothing, so a framing header on it protects nothing, and it can do harm. An app that allows a framer renews its token through three redirects inside the frame: the guard's, core's and the callback's. None of them can carry the app's policy, because the guard answers before the app runs. A browser that checks `X-Frame-Options` on each hop, as Chromium may, would stop the renewal there. An app's own redirects still carry the header, since Express and Go set it before they know the status. So an app that allows a framer sends its policy on every answer, redirects included.
- **Why that header and not a policy.** The obvious choice is `Content-Security-Policy: frame-ancestors 'self'`. But an app may send a policy of its own, and two policy headers don't survive every stack: on Express the app's `res.set` replaces the guard's, and on Next the guard's makes Next drop the app's. `X-Frame-Options` is a different header, so the two never meet. A browser obeys it unless a policy on the same answer has `frame-ancestors`. So an app's policy without `frame-ancestors`, such as one that only sets `default-src`, leaves the protection on.
- **An app changes who may frame it in its own policy, and only there.** To allow a framer, an app sets `Content-Security-Policy: frame-ancestors 'self' https://hub.<domain>` on its answers, and the browser follows that. To refuse every framer, its own origin included, it sends `frame-ancestors 'none'`. So `guarded()` needs no option for it.
- **Setting `X-Frame-Options` in the app isn't supported.** On Next the guard's value always wins: Next copies the proxy's headers onto the answer first, and then drops a route's header of the same name (`send-response.js`). On the other stacks the app's value may win. Don't make the stacks agree. Tell the app's author to use `frame-ancestors`, which works the same on every stack.
- **Each stack's way.** Express and Go set the headers before the handler runs, so nothing wraps the response. Hono and Start add them to the answer on its way out, where the app set none; an answer whose headers can't be changed, such as `Response.redirect()` or one passed through from `fetch`, is copied first. Next's guard answers before the page exists, so it sets them on the answer it passes on. Prove each with a route that sends its own policy: both headers arrive, and the app's policy is unchanged.
- **Once each.** No answer carries either header twice. Express's adapter appends the headers of the guard's own answers, so a header set before the handler must not be appended again. In dev the Go stack passes Vite's answers through `httputil.ReverseProxy`, which adds the upstream's headers to the ones already set, and Vite's error pages send `nosniff` themselves. The Go template's proxy drops the upstream's copy of both headers.
- **Go's upgrade may carry them, and that's fine.** Go sets the headers before the handler, so the 101 that answers Vite's hot-update socket may carry them too. They do no harm there, and nothing here promises they arrive. Don't wrap the `ResponseWriter` to take them off: a wrapper loses `http.Hijacker`, and the socket with it.
- **Next's pages.** A Next page can't set its own headers, and `proxy.ts` is all `guarded()`. So a page allows a framer through `headers()` in `next.config.ts`, and a route handler through its own answer. Prove both: the policy arrives beside the guard's header.
- **Core.** Core sends `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'` and `nosniff` on every answer that isn't a redirect, errors and CORS preflights included. Its redirects carry `nosniff` alone, for the reason above. Register the headers before `cors()`, or a preflight's answer misses them.
- **HSTS where the install is https.** Core and the guard send `Strict-Transport-Security` when the install's origin is https. Pick the max-age and say why in the comments. No `includeSubDomains`: the domain may hold hosts robkit doesn't run.
- **What isn't covered.** Files a stack serves without the guard, such as an app's built scripts and styles, don't carry the headers, and aren't pages. The hub isn't guarded: tickets 10 and 11 give it core's three headers, with `DENY` and not `SAMEORIGIN`, from `robkit()` in dev and `servePage()` in production. Say both in the comments. And a frame isn't the only way to steal a click: a sibling app can still open admin in a window of its own and time a double-click onto one of its buttons. These headers don't stop that.
- **Docs.** `SECURITY.md` says no guarded app can be framed from another origin by default, and what isn't covered: the opened window, so nobody reads it as "admin's clicks are safe", and the hub, which can be framed until tickets 10 and 11. Each stack's `AGENTS.md` says how to allow a framer. Next's says where a page and a route handler each set the policy, and that its own `X-Frame-Options` won't arrive.
